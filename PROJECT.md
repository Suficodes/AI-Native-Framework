# ai-native-control-tower

> AI-Native Enterprise Control Tower — a CAIO-facing prototype that shows how DEWA becomes an AI-native organization: organization → job → activity → Quality Procedure → process → human/agent allocation → AI initiative → agent harness → D2D delivery → performance → value realization → token economics → strategic outcomes, in one connected product.

## Goals

- Demonstrate the full AI-native transformation chain (org → QP → process → agent → harness → D2D → value → tokens → strategy) as one coherent, navigable product — not a set of disconnected dashboards.
- Give CAIO/CIO/EVP a presentation-ready tool: Executive Overview → drill-down through every module → a final interactive "AI-Native Enterprise Map" with a scripted Story Mode.
- "Done" for v1 = all 16 modules real (not stub) with mock data, the two named worked examples (Senior Business Analyst position, D2D Documentation Agent + its harness) fully populated, and a README with the SAP Neptune implementation mapping.

## Stack

See `/architecture` (live) or `public/tech-stack.json`.

_Stack deviations:_
- **No backend.** This prototype is frontend-only: mock TypeScript data (`frontend/src/data/`) served through local `mockApi.ts` functions, consumed via local React state. No FastAPI, no Postgres, no Docker. This is an explicit instruction from the requirements doc (Section 1: "No backend required for the first prototype... No external API keys... No paid dependencies"), not an oversight. A follow-up phase would move `mockApi.ts`'s data into the standard DAK FastAPI+Postgres backend.
- **Design system:** Astryx + the bundled `dewa` theme (DEWA green `#007560`, already the Astryx default), extended with this project's own `frontend/src/dewa/DESIGN.md` token set (Dubai font, 5/7/15/20/100px radius scale, pill buttons) layered on top as `theme-control-tower.css` + a `DewaButton` wrapper — see that file for specifics.
- **Charts:** `recharts`. **Node-link graphs** (org chart, harness designer, final Enterprise Map): `@xyflow/react` + `@dagrejs/dagre` for auto-layout where edges aren't a pure tree. Both MIT-licensed, no paid dependencies.

### Phase 2 — AI Playbook module (2026-08-01)

### Phase 2 — Step 9: Performance + Value Realization + Token Economics (2026-08-01)

Three modules, plus the token-ledger rebuild the AI Playbook step had flagged and deferred to here.

**Token ledger rewritten bottom-up.** Section 15 requires drill-down from enterprise to a single transaction, which only means anything if each level equals the sum of its children. The old generator drew every level independently from one 5K–8M range, so a Transaction row could exceed the Enterprise row and no rollup agreed with its parts. It now generates agent-month atoms from per-call characteristics, splits them down (Harness → Skill → Model, with an exact-remainder `split()` so rounding never drifts) and sums them up (Process → Department → Division → Enterprise), across six monthly periods so the trend charts have a real trend. 870 rows; a test asserts all 444 parent rows reconcile exactly on cost, tokens, calls and outcomes, and that no child ever exceeds its parent. The ledger's "Skill" level now references the real `ReusableSkill` registry (skills are seeded before the ledger) rather than inventing parallel labels. Scale is credible at last: ~ê14K/month enterprise token cost over 73K calls and 610M tokens.

**Performance** (Section 13): separate Agent and Human views, as the doc demands. Agent view carries all 13 KPIs, the 7-dimension weighted index — with the weights exported once and read by both the seed that applies them and the UI that explains them — and the six result outcomes. The Human view's nine dimensions deliberately contain no prompt-count metric ("Do not measure employees only by prompt count"), and a test asserts no KPI key contains "prompt". **Value Realization** (Section 14): eight tabs over one record set, the nine-gate approval workflow, all twelve benefit and eleven cost categories, and an executive dashboard whose four headline formulas come from `lib/calc.ts` rather than being recomputed. **Token Economics** (Section 15): eleven KPI cards, the nine-level drill-down, eight visualizations, and the budget-control register.

**Lessons**

- Three seed defects surfaced, each by a different mechanism:
  1. **A unit test caught an impossible number.** `capacityRedeployedHours` was drawn independently of `capacityReleasedHours`, so the fleet redeployed 2,061 hours it had only released 1,965 of — a redeployment rate over 100%. Redeployed hours are now a fraction of released hours. Worth noting the assertion that caught it was a *relationship* between two fields, not a range check; range checks on each field separately would have passed forever.
  2. **A foreign key pointed at the wrong entity type.** `VRRecord.agentId` was filled from `AIInitiative.agentOwnerId` — which is an *employee* for most initiatives — and `harnessId` was never populated at all, so 14 of 15 VR records had no agent. Both are now resolved through initiative → process → serving agent → its harness. The existing FK test only checked for dangling references within one collection, which is why this survived: an ID that resolves in the *wrong* table is not a dangling reference. The new spec checks each FK against its own entity type.
  3. **A pre-existing double-count became a real bug.** `computeTokenCostByModel` summed `cost` across every ledger row; harmless-ish when levels were unrelated, but with a nesting hierarchy it counts the same spend once per level. Now reads Model-level rows only.
- **Browser verification caught four more the tests could not**, all display-layer: money KPIs rendering as bare numbers with no dirham glyph; sub-dirham costs rounding to `ê0`; a "Calls" line flattened invisibly against a tokens axis three orders of magnitude larger; and duplicate axis ticks where 2,500 and 3,400 both formatted as "3K". The money fix is the useful one — `KpiCard` gained a `currency` prop, which also **closed the Step 4 debt** where `KpiGrid.jsx` used `prefix="AED "` (rendering the letters instead of the glyph).
- Astryx's `Tab` renders a plain `<button>` with **no `role="tab"`** and duplicates its label into two spans, so `[role="tab"]` selectors find nothing and `textContent === label` never matches. Not a bug I introduced, but it affects every tabbed module (Processes, Agents, VR, Performance) — logged for Step 12's accessibility pass.
- `tokenUsageForAgent` used `find` on agent-level rows; with six periods that silently returns the *oldest* month. Now pinned to the latest period, with a separate `tokenTrendForAgent` for the series. Any `find` over a collection that gains a time dimension is a latent bug of this shape.

### Phase 2 — Step 10: Observability + Strategic Alignment (2026-08-01)

**Data gaps closed first** — the modules could not be built honestly without them:
- `AgentRunEvent` gained `signal` (guardrail / security / token anomaly / cost anomaly), `toolName`, `evaluationScorePct`, `approver`/`approvalDecision`, and a `Running` status; `Trace.outcome` gained `InProgress`. Four of the doc's required counters had nothing to count before this, and the log views had nothing but timestamps to show. **Lessons**

- **The strategy map exposed a structural data defect.** Its agent layer came out with a single node. Root cause: only **1 of 15 agents** had `assignedProcessIds` and **4 of 126 process steps** named an agent — agents were almost entirely disconnected from processes. That silently degraded the Agents module's Process Assignments tab, the playbook's agent resolution, and Token Economics' process attribution too; it just never rendered as an obvious hole until a graph tried to draw the link. Fixed at the source (non-D2D steps now draw an agent from their owning section) plus a `backfillAgentAssignments` pass in `dataset.ts` — agents are constructed *before* processes exist, so they cannot know their own assignments at build time. Now 10 of 15 agents carry processes and 8 carry Quality Procedures, with no dangling keys.
- **The QP-01 ID collision from Step 5 recurred verbatim.** `TRACE-001` is hand-authored for the doc's worked example, then a loop calls `nextTraceId()` — which starts at `TRACE-001`, because the hardcoded push never advanced the counter. The duplicate shadowed the worked example, and a test asserting the trace's agent caught it. Same shape, same fix (burn one ID). The general rule this is the second instance of: **a hardcoded ID sitting beside a generator that shares its counter is always a collision.** Added a sweep over all ten ID-generating collections — every one is now collision-free.
- Defaulted the strategy map to a single objective rather than all five. The full 71-node graph is correct but illegible at fit-view zoom, and a strategy map nobody can read is not showing anyone how initiatives derive from strategy.

### Phase 2 — Step 11: The AI-Native Enterprise Map (2026-08-01)

The doc calls Section 18 "the strongest and most visually impressive part of the prototype": a full-screen map of the whole transformation cycle with ten lenses, progressive disclosure, and a Story Mode.

Built to CONVENTIONS.md's central rule, literally: **one graph, one `applyLens()`**. `enterpriseMapGraph.ts` builds a single 403-node / 596-edge graph covering every level of the doc's primary hierarchy (Strategic Objectives → … → Token and Total Cost) with eleven kinds of cross-cutting edge. A lens is pure *data* — a spec naming the node and edge kinds it keeps and what it colours by — so there is no per-lens code path and an eleventh lens is one table entry. The seven "show only…" filters, the division scope, search and the flow toggles are all just options to that same function; a test asserts the shared graph is never mutated and that identical input yields identical output.

**Progressive disclosure** is the piece that makes 403 nodes usable. `discloseGraph()` hides collapsed subtrees and then **lifts every edge whose endpoint is hidden up to its nearest visible ancestor** — collapse a division and the value flowing out of an agent inside it still shows as value flowing out of the division, rather than silently disappearing. That is what keeps the map honest at every zoom level, and it is the direct answer to the doc's warning that the map "should remain understandable and not appear as an uncontrolled network of hundreds of nodes".

**Lessons**

- **Two data bugs the map found because a graph cannot hide them.** Divisions were orphaned from the enterprise root: their `parentId` pointed at the org id but the root node lives in its own id namespace, so `nid.org()` produced an id nothing matched. And the "process dependency" edge kind came out empty because **every D2D demand hardcoded `processId: PROC-D2D`** — D2D is the pipeline a demand flows *through*, not the process it changes, and collapsing the two erased the demand→process relationship for the whole app. Demands now target a real process in their own division.
- **Department and division nodes reported zero headcount** on the drill-down panel: employees are assigned to sections, so counting direct members only gives zero everywhere above. Fixed by reusing `organizationAggregates.headcountRollup` rather than re-deriving it — the rollup already existed and the map should have called it from the start.
- **A React shorthand/longhand style bug in three files.** `border` and `borderLeft` in one style object makes React warn on every rerender; the map rerenders on every hover and selection, so it produced ~50 console errors in a single click-through. The same pattern had been sitting in `OrgFlowNode.jsx` since Step 4 and never fired, because the org chart does not rerender its node styles. Worth noting the browser pass only surfaced it once a component rerendered often enough — a latent bug of this shape can sit dormant for six steps.
- **Story Mode floods the canvas unless it is scoped.** Eleven of the fourteen beats overrode the lens depth and rendered 79–114 nodes — the readability bound the default lens views are held to did not cover story overrides. Fixed by scoping the deep beats to the division that owns the D2D worked example, which is also the better narrative: a walkthrough is more persuasive drilling into one concrete division than gesturing at the whole enterprise at leaf level. The test now enforces the bound on story steps too.
